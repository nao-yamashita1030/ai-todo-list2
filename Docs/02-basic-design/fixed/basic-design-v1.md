# 基本設計書

## 1. システム構成

### 1.1 システム全体構成
```
[ユーザー]
    ↓ HTTPS
[Vercel (Next.js App)]
    ↓
[Next.js API Routes]
    ↓
[Clerk (認証)] ← [Supabase (PostgreSQL)]
```

**構成要素:**
- **フロントエンド**: Next.js（Vercel上でホスティング）
- **バックエンド**: Next.js API Routes
- **認証**: Clerk
- **データベース**: Supabase（PostgreSQL）

### 1.2 システム構成要素
- **クライアント**: Webブラウザ（PC、スマートフォン、タブレット）
- **フロントエンドサーバー**: Vercel（Next.js）
- **バックエンドAPI**: Next.js API Routes
- **認証サービス**: Clerk
- **データベース**: Supabase（PostgreSQL）

### 1.3 システム間連携
- **クライアント ↔ Next.js**: HTTPS通信
- **Next.js ↔ Clerk**: Clerk SDK経由で認証情報を取得
- **Next.js ↔ Supabase**: Supabaseクライアント経由でデータベースにアクセス
- **既存システムとの連携**: 特に要件なし

## 2. アーキテクチャ

### 2.1 アーキテクチャパターン
**モノリシックアーキテクチャ（Next.js Full-Stack）**
- Next.jsのApp Routerを使用したフルスタックアプリケーション
- フロントエンドとバックエンドを同一プロジェクトで管理
- Server ComponentsとClient Componentsを適切に使い分け

### 2.2 レイヤー構成
1. **プレゼンテーション層**: Next.js Pages/Components（React）
2. **ビジネスロジック層**: Server Actions / API Routes
3. **データアクセス層**: Prisma ORM / Supabase Client
4. **データベース層**: Supabase（PostgreSQL）

### 2.3 技術スタック
- **フロントエンド**: Next.js 14.2.25、React 18.2.0、TypeScript 5.2.2
- **UIコンポーネント**: shadcn/ui、Tailwind CSS 3.4.1
- **バックエンド**: Next.js API Routes
- **データベース**: Supabase（PostgreSQL）
- **ORM**: Prisma 5.11.0
- **認証**: Clerk 6.12.9
- **デプロイ**: Vercel
- **フォーム処理**: Server Actions、Zod 3.x

## 3. 主要機能の設計

### 3.1 機能一覧
要件定義書に基づく主要機能:

1. **認証機能**
   - ログイン/ログアウト
   - ユーザー登録

2. **TODO管理機能**
   - TODOの作成
   - TODOの編集
   - TODOの削除
   - TODOの完了/未完了切り替え
   - TODOの一覧表示

3. **検索・フィルタリング機能**
   - TODOの検索
   - フィルタリング（完了/未完了、優先度、カテゴリなど）

4. **分類・整理機能**
   - カテゴリ/タグ機能
   - プロジェクト/フォルダ機能
   - 優先度設定
   - 期限日設定
   - リマインダー機能

5. **共有・コラボレーション機能**
   - 複数ユーザー対応（共有機能）
   - コメント機能
   - 履歴管理（変更履歴の確認）

### 3.2 機能設計
各機能の設計概要:

#### 認証機能
- Clerkを使用した認証
- セッション管理はClerkが自動的に処理
- 認証状態はServer Componentsで確認

#### TODO管理機能
- Server Componentsでデータ取得
- Server Actionsでデータ作成・更新・削除
- リアルタイム更新は必要に応じて実装

#### 検索・フィルタリング機能
- クライアントサイドでのフィルタリング
- サーバーサイドでの検索（必要に応じて）

#### 分類・整理機能
- カテゴリ、タグ、プロジェクト/フォルダはデータベースで管理
- 優先度、期限日はTODOエンティティの属性として管理
- リマインダーは期限日ベースで実装

#### 共有・コラボレーション機能
- プロジェクト/フォルダ単位で共有権限を管理
- コメントはTODOに関連付けて管理
- 変更履歴は別テーブルで管理

### 3.3 機能間の連携
- 認証機能はすべての機能の前提条件
- TODO管理機能は検索・フィルタリング機能と連携
- 分類・整理機能はTODO管理機能と密接に連携
- 共有・コラボレーション機能はTODO管理機能と連携

## 4. データベース設計（概要）

### 4.1 データベース選定
- **データベース**: Supabase（PostgreSQLベース）
- **選定理由**: 
  - 無料プランで利用可能
  - PostgreSQLの強力な機能を活用可能
  - Prisma ORMとの親和性が高い
  - リアルタイム機能や認証機能も提供（今回はClerkを使用）

### 4.2 主要テーブル構成
主要なテーブル（詳細は詳細設計フェーズで定義）:

1. **users** - ユーザー情報（Clerkで管理、必要に応じて拡張）
2. **projects** - プロジェクト/フォルダ情報
3. **todos** - TODO情報
4. **categories** - カテゴリ情報
5. **tags** - タグ情報
6. **todo_tags** - TODOとタグの関連テーブル
7. **comments** - コメント情報
8. **histories** - 変更履歴情報
9. **project_members** - プロジェクトメンバー情報（共有機能用）

### 4.3 データリレーション
主要なリレーション（詳細は詳細設計フェーズで定義）:

- **users** ←→ **projects** (多対多: project_members経由)
- **projects** ←→ **todos** (1対多)
- **todos** ←→ **categories** (多対1)
- **todos** ←→ **tags** (多対多: todo_tags経由)
- **todos** ←→ **comments** (1対多)
- **todos** ←→ **histories** (1対多)

### 4.4 データフロー
1. ユーザーがブラウザから操作
2. Next.js Server Components / API Routesでリクエスト受信
3. Clerkで認証確認
4. Prisma経由でSupabaseにアクセス
5. データ取得・更新・削除
6. 結果をクライアントに返却

## 5. API設計（概要）

### 5.1 API設計方針
- **原則**: Server Componentsでのデータフェッチを優先
- **API Routes**: POST/PATCH/PUT/DELETEのみ（GETはServer Componentsで実装）
- **認証**: すべてのAPIでClerkの認証チェックを実施
- **エラーハンドリング**: 適切なHTTPステータスコードとエラーメッセージを返却

### 5.2 API一覧
主要なAPIエンドポイント（詳細は詳細設計フェーズで定義）:

1. **TODO管理API**
   - POST `/api/todos` - TODO作成
   - PATCH `/api/todos/[id]` - TODO更新
   - DELETE `/api/todos/[id]` - TODO削除

2. **プロジェクト管理API**
   - POST `/api/projects` - プロジェクト作成
   - PATCH `/api/projects/[id]` - プロジェクト更新
   - DELETE `/api/projects/[id]` - プロジェクト削除

3. **コメント管理API**
   - POST `/api/comments` - コメント作成
   - PATCH `/api/comments/[id]` - コメント更新
   - DELETE `/api/comments/[id]` - コメント削除

### 5.3 API仕様概要
- **リクエスト形式**: JSON
- **レスポンス形式**: JSON
- **エラーレスポンス**: エラーオブジェクトとHTTPステータスコード
- **バリデーション**: Zodスキーマを使用

### 5.4 認証・認可方式
- **認証**: Clerkの認証トークンを確認
- **認可**: ユーザーIDとリソースの所有者を照合
- **プロジェクト共有**: project_membersテーブルで権限管理

## 7. セキュリティ設計

### 7.1 認証・認可設計
- **認証**: Clerkを使用した認証
- **セッション管理**: Clerkが自動的に処理
- **認可**: 
  - リソースの所有者のみが編集・削除可能
  - プロジェクトメンバーのみがプロジェクト内のTODOにアクセス可能
  - データベースレベルでRow Level Security (RLS) を設定

### 7.2 データ保護設計
- **個人情報の暗号化**: Supabaseの暗号化機能を活用
- **パスワード管理**: Clerkが自動的にハッシュ化・管理
- **データベースアクセス**: Prisma ORMを使用してSQLインジェクション対策

### 7.3 通信セキュリティ設計
- **HTTPS通信**: Vercelが自動的にHTTPSを提供
- **CORS設定**: 適切なCORS設定を実施
- **セキュリティヘッダー**: Next.jsのセキュリティヘッダーを設定

## 8. エラーハンドリング

### 8.1 エラー分類
- **認証エラー**: 401 Unauthorized
- **認可エラー**: 403 Forbidden
- **バリデーションエラー**: 400 Bad Request
- **リソース不存在エラー**: 404 Not Found
- **サーバーエラー**: 500 Internal Server Error

### 8.2 エラー処理方針
- **クライアントサイド**: ユーザーフレンドリーなエラーメッセージを表示
- **サーバーサイド**: 適切なHTTPステータスコードとエラーメッセージを返却
- **ログ**: エラー情報をログに記録（本番環境では機密情報を除外）

### 8.3 ログ設計
- **開発環境**: コンソールに詳細なログを出力
- **本番環境**: Vercelのログ機能を活用
- **ログレベル**: Error、Warn、Info、Debug
- **機密情報**: パスワードやトークンなどの機密情報はログに記録しない

### 9.1 パフォーマンス目標
- **レスポンスタイム**: 3秒以内（要件定義より）

### 9.2 パフォーマンス対策

- **コード分割**: 動的インポートを活用
- **データベースクエリ**: 適切なインデックス設定、N+1問題の回避

### 9.3 キャッシュ設計
- **Next.jsキャッシュ**: Next.jsのキャッシュ機能を活用
- **データベースクエリ**: Prismaのクエリ結果を適切にキャッシュ
- **ブラウザキャッシュ**: 静的アセットのキャッシュ設定
