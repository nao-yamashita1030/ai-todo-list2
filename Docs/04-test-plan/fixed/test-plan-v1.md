# テスト計画書

## 1. テスト方針

### 1.1 テストの目的

本テスト計画書は、TODOリスト管理WEBアプリケーションの品質を確保するため、以下の目的でテストを実施します：

- **機能の正確性の確認**: 要件定義で定義された機能が正しく動作することを確認
- **非機能要件の達成確認**: パフォーマンス、セキュリティ、可用性などの非機能要件が満たされていることを確認
- **ユーザビリティの確認**: ユーザーが直感的に操作できることを確認
- **回帰テスト**: 変更による既存機能への影響がないことを確認

### 1.2 テストの範囲

#### 機能テストの範囲
- **認証機能**: ログイン/ログアウト、ユーザー登録（Clerkが提供）
- **TODO管理機能**: 作成、編集、削除、完了/未完了切り替え、一覧表示
- **検索・フィルタリング機能**: TODOの検索、フィルタリング（完了/未完了、優先度、カテゴリなど）
- **分類・整理機能**: カテゴリ/タグ機能、プロジェクト/フォルダ機能、優先度設定、期限日設定、リマインダー機能
- **共有・コラボレーション機能**: 複数ユーザー対応、コメント機能、履歴管理

#### 非機能テストの範囲
- **パフォーマンステスト**: レスポンスタイム（3秒以内）、同時接続数（5人以下）
- **セキュリティテスト**: 認証・認可、データ保護、通信セキュリティ、脆弱性対策
- **互換性テスト**: モダンブラウザ（Chrome、Firefox、Safari、Edge）、レスポンシブデザイン
- **ユーザビリティテスト**: 直感的な操作、キーボードショートカット、アクセシビリティ

### 1.3 テストの除外範囲

以下の範囲はテストの対象外とします：

- **Clerkの認証機能**: Clerkが提供する機能のため、詳細なテストは実施しない（統合テストのみ）
- **Vercelのインフラ機能**: Vercelが提供する機能のため、詳細なテストは実施しない
- **Supabaseのデータベース機能**: Supabaseが提供する機能のため、詳細なテストは実施しない（データベース接続テストのみ）
- **将来検討機能**: 統計・レポート機能、エクスポート機能、インポート機能、ファイル添付機能

### 1.4 テストの基本方針

- **テスト駆動開発（TDD）の採用**: 可能な範囲でTDDを採用し、テストを先に作成してから実装する
- **自動テストの優先**: 手動テストよりも自動テストを優先し、回帰テストの効率化を図る
- **段階的なテスト実施**: 単体テスト → 結合テスト → システムテスト → 受入テストの順で実施
- **継続的なテスト実施**: 実装と並行してテストを実施し、早期に問題を発見する
- **テストカバレッジの確保**: 詳細設計で定義されたテストカバレッジ目標を達成する

## 2. テスト種別

### 2.1 単体テスト

#### 目的
個別のコンポーネント、関数、クラスが正しく動作することを確認する

#### 対象
- **Server Components**: TodoListPage、TodoDetailPage、ProjectListPageなど
- **Server Actions**: TODO作成、更新、削除、ステータス切り替えなど
- **Service Layer**: TodoService、ProjectService、CommentService、HistoryService
- **Utility Classes**: Validation、Auth
- **Client Components**: TodoForm、TodoList、TodoItem、CommentListなど

#### 実施方法
- **テストフレームワーク**: Jest、React Testing Library
- **テスト実行環境**: ローカル開発環境
- **Next.js 14 App Router対応**: Next.js 14のApp Routerに対応したJest設定を使用
  - `@testing-library/react` の最新版を使用
  - Server Componentsのテストには、Next.jsのテストユーティリティを使用
- **モック**: データベース、認証サービス、外部APIをモック化
  - **Server Components**: データフェッチをモック化（MSWを使用）
  - **Server Actions**: データベースアクセスをモック化
  - **Clerk認証**: Clerk SDKをモック化

#### 判定基準
- **Server Components**: テストカバレッジ60%以上
- **Server Actions**: テストカバレッジ80%以上
- **Service Layer**: テストカバレッジ90%以上
- **Utility Classes**: テストカバレッジ100%
- **Client Components**: テストカバレッジ70%以上
- すべてのテストケースが成功すること

### 2.2 結合テスト

#### 目的
複数のコンポーネントやモジュールが連携して正しく動作することを確認する

#### 対象
- **Server Actions**: TODO作成、更新、削除、ステータス切り替え、プロジェクト作成、更新、削除、コメント作成、更新、削除など
- **APIエンドポイント**: POST、PATCH、DELETEエンドポイント（Server ActionsとAPI Routesの両方）
- **画面遷移**: 各画面間の遷移
- **データフロー**: データの作成から表示までのフロー
- **認証・認可フロー**: 認証状態に応じた画面表示とAPIアクセス

#### 実施方法
- **テストフレームワーク**: Jest、Playwright（E2Eテスト）
- **テスト実行環境**: ローカル開発環境、テスト環境
- **テストデータ**: 事前に準備したテストデータを使用

#### 判定基準
- すべてのテストシナリオが成功すること
- APIエンドポイントが正しいレスポンスを返すこと
- 画面遷移が正しく動作すること
- データフローが正しく動作すること

### 2.3 システムテスト

#### 目的
システム全体が要件定義で定義された機能を満たしていることを確認する

#### 対象
- **機能要件**: 要件定義で定義されたすべての機能
- **非機能要件**: パフォーマンス、セキュリティ、互換性
- **画面遷移**: 基本設計で定義された画面遷移図に基づく遷移
- **エラーハンドリング**: エラーハンドリング詳細設計に基づくエラー処理

#### 実施方法
- **テストフレームワーク**: Playwright（E2Eテスト）
- **テスト実行環境**: テスト環境（Vercelのプレビュー環境）
- **テストデータ**: 本番環境に近いテストデータを使用

#### 判定基準
- すべての機能要件が満たされていること
- 非機能要件が満たされていること（レスポンスタイム3秒以内など）
- 画面遷移が正しく動作すること
- エラーハンドリングが正しく動作すること

- **パフォーマンス**: 実際の使用環境でのパフォーマンス

#### 実施方法
- **テスト実行環境**: 本番環境または本番環境に近い環境

### 2.6 セキュリティテスト

## 4. テスト環境

### 4.1 テスト環境構成

```
[開発者PC]
    ↓
[ローカル開発環境]
    ├→ [Next.js開発サーバー]
    ├→ [SQLiteデータベース]（開発環境、後でSupabaseに移行）
    └→ [Clerk開発環境]

[テスト環境]
    ├→ [Vercelプレビュー環境]
    ├→ [Supabaseテスト環境]
    └→ [Clerkテスト環境]

[本番環境]
    ├→ [Vercel本番環境]
    ├→ [Supabase本番環境]
    └→ [Clerk本番環境]
```

**注意**: 開発環境では初期段階でSQLiteを使用し、テスト環境・本番環境ではSupabase（PostgreSQL）を使用します。SQLiteからSupabaseへの移行は、実装フェーズのフェーズ2（データベーススキーマ作成）完了後、またはテスト環境構築時に実施します。

## 5. スケジュール

### 5.1 テスト実施スケジュール

テストは実装フェーズと並行して実施します：

1. **単体テスト**: 実装と並行して実施（継続的）
   - **実施期間**: 実装フェーズ全体（約2週間）
   - **実施頻度**: 各機能実装完了時に実施
2. **結合テスト**: 機能単位で実装完了後に実施
   - **実施期間**: 各機能実装完了後（約1週間）
   - **実施頻度**: 機能単位で実施
3. **システムテスト**: 主要機能の実装完了後に実施
   - **実施期間**: 主要機能実装完了後（約3-5日）
   - **実施頻度**: 主要機能実装完了時に実施
4. **受入テスト**: システムテスト完了後に実施
   - **実施期間**: システムテスト完了後（約2-3日）
   - **実施頻度**: システムテスト完了時に実施
5. **パフォーマンステスト**: システムテストと並行して実施
   - **実施期間**: システムテストと並行（約2-3日）
   - **実施頻度**: システムテスト完了時に実施
6. **セキュリティテスト**: システムテストと並行して実施
   - **実施期間**: システムテストと並行（約2-3日）
   - **実施頻度**: システムテスト完了時に実施
7. **ユーザビリティテスト**: 受入テストと並行して実施
   - **実施期間**: 受入テストと並行（約1-2日）
   - **実施頻度**: 受入テスト完了時に実施

### 5.1.1 CI/CDへのテスト統合

- **自動テスト実行**: GitHub ActionsまたはVercelのCI/CD機能を使用して、プッシュ時に自動的にテストを実行
- **テスト実行タイミング**:
  - プルリクエスト作成時: 単体テスト、結合テストを自動実行
  - マージ前: すべてのテストを自動実行
  - デプロイ前: システムテスト、パフォーマンステストを自動実行
- **テスト結果の通知**: テスト失敗時にSlackやメールで通知（必要に応じて）
- **テストカバレッジレポート**: テストカバレッジレポートを自動生成し、プルリクエストに表示

### 5.2 マイルストーン

- **マイルストーン1**: 単体テストカバレッジ目標達成
- **マイルストーン2**: 結合テスト完了
- **マイルストーン3**: システムテスト完了
- **マイルストーン4**: 受入テスト完了
- **マイルストーン5**: リリース準備完了

### 5.3 リソース計画

- **テスト実施者**: 開発者（実装者とは別の担当者が望ましい）
- **テスト環境**: Vercelプレビュー環境、Supabaseテスト環境
- **テストツール**: 上記のテストツールを使用

## 6. テスト実施体制

### 6.1 テストチーム構成

小規模チームのため、開発者がテストも実施します：

- **テストリーダー**: プロジェクトリーダー
- **テスト実施者**: 開発者（実装者とは別の担当者が望ましい）

### 6.2 役割分担

- **テストリーダー**: テスト計画の策定、テスト結果のレビュー、品質管理
- **テスト実施者**: テストケースの作成、テストの実施、バグレポートの作成

### 6.3 コミュニケーション体制

- **日次**: テスト進捗の報告
- **週次**: テスト結果のレビュー、バグの優先順位付け
- **マイルストーン**: テスト完了報告

## 7. テスト結果管理

### 7.1 テスト結果の記録方法

- **テスト結果**: テストケースごとに記録
- **記録場所**: テスト実行記録ファイル（`Docs/07-testing/`）
- **記録形式**: マークダウンファイルまたはスプレッドシート

### 7.2 バグ管理

- **バグ管理方法**: GitHub Issuesを使用
- **バグの分類**: 重大度（Critical、High、Medium、Low）と優先度（P0、P1、P2、P3）
- **バグの追跡**: バグの状態（新規、対応中、修正済み、確認済み、クローズ）

### 7.3 テスト進捗管理

- **進捗管理方法**: テスト計画書に基づく進捗管理
- **進捗報告**: 週次で進捗を報告
- **進捗指標**: テスト実施率、テスト成功率、バグ発見数

### 7.4 テスト報告

- **テスト報告のタイミング**: 各マイルストーン完了時
- **テスト報告の内容**: テスト実施結果、発見されたバグ、品質評価

## 8. リスク管理

### 8.1 テストリスク

- **リスク1**: テスト環境の構築が遅延する
  - **影響**: テスト実施が遅延する
  - **対策**: 早期にテスト環境を構築する
- **リスク2**: テストデータの準備が不十分
  - **影響**: テストが十分に実施できない
  - **対策**: テストデータを事前に準備する
- **リスク3**: バグの修正が遅延する
  - **影響**: テスト完了が遅延する
  - **対策**: バグの優先順位を明確にする

### 8.2 リスク対策

- **早期のテスト環境構築**: 実装開始前にテスト環境を構築する
- **テストデータの事前準備**: テストデータを事前に準備する
- **バグの優先順位付け**: バグの重大度と優先度を明確にする

### 8.3 エスカレーション

- **重大なバグ発見時**: 即座にプロジェクトリーダーに報告
- **テスト遅延時**: プロジェクトリーダーに報告し、スケジュールを調整
- **品質基準未達成時**: プロジェクトリーダーに報告し、対応を検討

## 9. 品質基準

### 9.1 テスト完了基準

以下の条件をすべて満たした場合、テスト完了とします：

- **単体テスト**: テストカバレッジ目標を達成し、すべてのテストが成功すること
- **結合テスト**: すべてのテストシナリオが成功すること
- **システムテスト**: すべての機能要件と非機能要件が満たされていること
- **受入テスト**: ユーザーが満足できる品質であること
- **バグ**: Critical、Highのバグがすべて修正されていること

### 9.2 品質目標

- **テストカバレッジ**: 詳細設計で定義された目標を達成
- **バグ発見率**: 実装フェーズで早期にバグを発見する
- **バグ修正率**: Critical、Highのバグは100%修正する
- **パフォーマンス**: レスポンスタイム3秒以内を達成

### 9.3 品質メトリクス

- **テストカバレッジ**: コードカバレッジツールで測定
- **バグ発見数**: GitHub Issuesで管理
- **バグ修正率**: バグの修正状況を追跡
- **パフォーマンス**: Lighthouse、WebPageTestで測定
