# 運用計画書

## 1. デプロイ計画

### 1.1 デプロイ環境

#### 本番環境
- **プラットフォーム**: Vercel
- **リージョン**: 自動選択（最適なリージョン）
- **ドメイン**: Vercelが提供するドメイン、またはカスタムドメイン
- **SSL証明書**: Vercelが自動的に管理

#### ステージング環境
- **プラットフォーム**: Vercel（プレビュー環境）
- **用途**: 本番デプロイ前の最終確認
- **アクセス**: 開発者のみアクセス可能

#### 開発環境
- **プラットフォーム**: ローカル開発環境
- **用途**: 開発・テスト

### 1.2 デプロイ手順

#### 自動デプロイ（推奨）
1. **開発**: 機能ブランチで開発
2. **プルリクエスト**: mainブランチへのプルリクエストを作成
3. **レビュー**: コードレビューを実施
4. **マージ**: mainブランチにマージ
5. **自動デプロイ**: Vercelが自動的に本番環境にデプロイ

#### 手動デプロイ（緊急時）
1. **Vercelダッシュボード**: Vercelのダッシュボードにアクセス
2. **デプロイ**: 手動でデプロイを実行
3. **確認**: デプロイ完了を確認

### 1.3 デプロイスケジュール

- **通常デプロイ**: 機能追加・修正時（随時）
- **緊急デプロイ**: 重大なバグ修正時（即座）
- **メンテナンスデプロイ**: 定期メンテナンス時（事前通知）

### 1.4 ロールバック計画

#### ロールバック手順
1. **Vercelダッシュボード**: Vercelのダッシュボードにアクセス
2. **デプロイ履歴**: 前回の正常なデプロイを選択
3. **ロールバック**: 前回のデプロイにロールバック
4. **確認**: ロールバック完了を確認

#### ロールバック判定基準
- 重大なバグが発見された場合
- パフォーマンスが大幅に低下した場合
- セキュリティ問題が発見された場合

### 1.5 デプロイチェックリスト

デプロイ前に以下の項目を確認します：

- [ ] テストがすべて成功している
- [ ] コードレビューが完了している
- [ ] 環境変数が正しく設定されている
- [ ] データベースマイグレーションが完了している（該当する場合）
- [ ] ドキュメントが更新されている（該当する場合）
- [ ] バックアップが取得されている（該当する場合）

## 2. 監視・運用体制

### 2.1 監視項目

#### アプリケーション監視
- **レスポンスタイム**: 各APIエンドポイントの応答時間
- **エラー率**: エラーの発生率
- **リクエスト数**: リクエストの総数
- **アクティブユーザー数**: 同時アクセスユーザー数

#### インフラ監視
- **サーバーリソース**: CPU、メモリ、ディスク使用率
- **ネットワーク**: 帯域幅、レイテンシ
- **データベース**: 接続数、クエリ実行時間

#### ビジネス監視
- **ユーザー登録数**: 新規ユーザー登録数
- **TODO作成数**: TODOの作成数
- **プロジェクト作成数**: プロジェクトの作成数

### 2.2 監視ツール

#### Vercel Analytics
- **用途**: パフォーマンス分析、エラー監視
- **機能**: Core Web Vitals、エラーログ、リクエスト分析

#### Supabase Dashboard
- **用途**: データベース監視
- **機能**: クエリパフォーマンス、接続数、ストレージ使用量

#### Clerk Dashboard
- **用途**: 認証監視
- **機能**: ユーザー数、認証エラー、セッション管理

### 2.3 アラート設定

#### アラート条件
- **エラー率**: エラー率が5%を超えた場合
- **レスポンスタイム**: レスポンスタイムが5秒を超えた場合
- **データベース接続**: データベース接続エラーが発生した場合
- **認証エラー**: 認証エラーが急増した場合

#### アラート通知先
- **メール**: 開発者にメール通知
- **Slack**: Slackチャンネルに通知（設定する場合）

### 2.4 運用体制

小規模チームのため、開発者が運用も担当します：

- **運用責任者**: プロジェクトリーダー
- **運用担当者**: 開発者

### 2.5 オンコール体制

- **オンコール**: 開発者が担当（必要に応じて）
- **対応時間**: 平日9:00-18:00（緊急時は24時間対応）

### 2.6 運用マニュアル

運用マニュアルは以下の場所に保管します：

## 3. バックアップ・リカバリ

### 3.1 バックアップ方針

- **自動バックアップ**: Supabaseの自動バックアップ機能を活用
- **手動バックアップ**: 重要な変更前には手動でバックアップを取得
- **バックアップ保持**: 無料プラン範囲内で可能な限り保持

### 3.2 バックアップ対象

- **データベース**: Supabaseのデータベース全体
- **環境変数**: Vercelの環境変数（手動でエクスポート）

### 3.3 バックアップスケジュール

- **自動バックアップ**: Supabaseが自動的に実施（無料プランの範囲内）

3. **確認**: 環境変数が正しく設定されていることを確認

### 3.6 リカバリテスト計画

- **テスト頻度**: 四半期に1回
- **テスト内容**: バックアップからのリカバリをテスト
- **テスト結果**: テスト結果を記録

## 4. 障害対応手順

### 4.1 障害レベル定義

#### Critical（緊急）
- **定義**: システム全体が使用できない状態
- **対応時間**: 即座に対応
- **例**: データベース接続エラー、認証サービス障害

#### High（高）
- **定義**: 主要機能が使用できない状態
- **対応時間**: 1時間以内に対応
- **例**: TODO作成機能が動作しない、プロジェクト作成機能が動作しない

#### Medium（中）
- **定義**: 一部機能が使用できない状態
- **対応時間**: 4時間以内に対応
- **例**: 検索機能が動作しない、フィルタリング機能が動作しない

#### Low（低）
- **定義**: 軽微な問題、ユーザー体験への影響が小さい
- **対応時間**: 1営業日以内に対応
- **例**: UIの表示不具合、軽微なエラーメッセージ

### 4.2 障害検知方法

- **自動検知**: Vercel Analytics、Supabase Dashboard、Clerk Dashboardのアラート
- **ユーザー報告**: ユーザーからの報告（メール、GitHub Issues）
- **定期監視**: 定期的な監視ダッシュボードの確認

### 4.3 障害対応フロー

1. **障害検知**: アラートまたはユーザー報告で障害を検知
2. **障害レベル判定**: 障害レベルを判定
3. **初期対応**: 障害の影響範囲を確認
4. **原因調査**: ログを確認し、原因を調査
5. **対応実施**: 原因に応じた対応を実施
6. **復旧確認**: 復旧を確認
7. **事後対応**: 再発防止策を検討

### 4.4 エスカレーション基準

- **Critical**: 即座にプロジェクトリーダーに報告
- **High**: 1時間以内にプロジェクトリーダーに報告
- **Medium**: 4時間以内にプロジェクトリーダーに報告
- **Low**: 1営業日以内にプロジェクトリーダーに報告

### 4.5 障害対応マニュアル

障害対応マニュアルは以下の内容を含みます：

- **障害レベル定義**: 上記の障害レベル定義
- **障害対応フロー**: 上記の障害対応フロー
- **よくある障害と対応**: 過去の障害事例と対応方法
- **連絡先**: 緊急時の連絡先

### 4.6 インシデント管理

- **インシデント記録**: GitHub Issuesでインシデントを記録
- **インシデント分析**: インシデントの原因分析を実施
- **再発防止**: 再発防止策を検討・実施

## 5. 保守計画

### 5.1 保守方針

- **継続的な改善**: ユーザーフィードバックに基づく継続的な改善
- **セキュリティ**: セキュリティパッチの迅速な適用
- **パフォーマンス**: パフォーマンスの継続的な監視と改善
- **ドキュメント**: ドキュメントの継続的な更新

### 5.2 定期メンテナンス

#### 週次メンテナンス
- **監視ダッシュボードの確認**: エラー、パフォーマンスの確認
- **ログの確認**: エラーログの確認

#### 月次メンテナンス
- **依存パッケージの更新**: セキュリティパッチの適用
- **バックアップの確認**: バックアップが正常に取得されていることを確認
- **パフォーマンスレビュー**: パフォーマンスのレビュー

#### 四半期メンテナンス
- **リカバリテスト**: バックアップからのリカバリテスト
- **セキュリティ監査**: セキュリティの監査
- **ドキュメント更新**: ドキュメントの更新

### 5.3 セキュリティパッチ適用

- **適用方針**: セキュリティパッチは迅速に適用する
- **適用タイミング**: セキュリティパッチがリリースされたら、1週間以内に適用
- **適用手順**: 
  1. セキュリティパッチの確認
  2. テスト環境でテスト
  3. 本番環境に適用
  4. 動作確認

### 5.4 バージョンアップ計画

#### Next.js、React、TypeScript
- **バージョンアップ方針**: メジャーバージョンアップは慎重に検討
- **マイナーバージョンアップ**: 定期的に実施（月次）
- **パッチバージョンアップ**: セキュリティパッチは即座に適用

#### その他の依存パッケージ
- **バージョンアップ方針**: セキュリティパッチは即座に適用
- **定期的な更新**: 月次で依存パッケージを確認・更新

### 5.5 保守体制

- **保守責任者**: プロジェクトリーダー
- **保守担当者**: 開発者

- **監視ツール**: Vercel Analytics、Supabase Dashboard、Clerk Dashboard
- **監視項目**: 認証エラー、異常なアクセスパターン、セキュリティアラート

- **脆弱性の検知**: 依存パッケージの脆弱性を定期的に確認
- **脆弱性の対応**: セキュリティパッチを迅速に適用
- **脆弱性の記録**: GitHub Issuesで脆弱性を記録

### 7.3 アクセス管理

- **環境変数管理**: Vercelの環境変数機能で管理
- **データベースアクセス**: Supabaseのアクセス制御を活用
- **認証管理**: Clerkの認証機能を活用

### 7.4 セキュリティインシデント対応

- **インシデント検知**: セキュリティアラート、異常なアクセスパターン

  1. インシデントの検知
  2. 影響範囲の確認

### 8.1 パフォーマンス監視

- **監視ツール**: Vercel Analytics、Lighthouse
- **監視項目**: 
  - レスポンスタイム（目標: 3秒以内）

### 8.2 パフォーマンスチューニング

- **チューニング方針**: パフォーマンスが低下した場合、原因を調査して改善
- **チューニング対象**: 
  - データベースクエリの最適化
  - キャッシュの活用
  - コードの最適化

### 8.3 キャパシティプランニング

- **現在のキャパシティ**: 小規模チーム（5人以下）を想定
- **将来の拡張**: チーム規模が拡大する場合は、プランをアップグレード
- **監視**: リソース使用率を監視し、必要に応じてプランを変更
