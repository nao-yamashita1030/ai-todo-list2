# 実装記録

## 1. 実装方針

### 1.1 実装の基本方針

- **段階的実装**: 機能を段階的に実装し、各機能が動作することを確認しながら進める
- **詳細設計に基づく実装**: 詳細設計書（`Docs/03-detailed-design/fixed/`）を参照して実装する
- **Server Components優先**: データフェッチはServer Componentsで実施し、API Routesは最小限に
- **Server Actions活用**: データ変更処理はServer Actionsを優先的に使用
- **型安全性の確保**: TypeScriptの型定義を適切に使用し、型安全性を確保
- **コンポーネントの再利用性**: 共通コンポーネントを適切に設計し、再利用性を高める

### 1.2 コーディング規約

- **Next.jsベストプラクティス**: `.cursor/rules/dev-rules/nextjs.mdc` を参照
- **ディレクトリ構造**: `.cursor/rules/dev-rules/nextjs.mdc` に記載の構造に従う
- **命名規則**: 
  - コンポーネント: PascalCase（例: `TodoList.tsx`）
  - 関数・変数: camelCase（例: `getTodos`）
  - 定数: UPPER_SNAKE_CASE（例: `MAX_TODO_COUNT`）
  - ファイル名: kebab-case（例: `todo-list.tsx`）
- **コードフォーマット**: Prettierを使用（設定があれば）
- **リンター**: ESLintを使用

### 1.3 開発環境

- **OS**: Windows 10/11
- **Node.js**: 最新のLTSバージョン
- **パッケージマネージャー**: npm または yarn
- **エディタ**: VS Code（推奨）
- **データベース**: 開発環境はSQLite（後でSupabaseに移行）
- **認証**: Clerk（開発環境と本番環境で同じ）

### 1.4 バージョン管理

- **Git**: 機能単位でコミット
- **コミットメッセージ**: `rules/commit-message.md` のルールに従う
- **ブランチ戦略**: mainブランチで直接開発（小規模プロジェクトのため）

## 4. 実装メモ

### 4.1 実装時の注意事項

- **詳細設計の参照**: 実装前に必ず詳細設計書（`Docs/03-detailed-design/fixed/`）を参照する
- **型定義の確認**: Prismaスキーマから生成される型定義を適切に使用する
- **エラーハンドリング**: 詳細設計の `06-error-handling.md` を参照してエラーハンドリングを実装する
- **セキュリティ**: 詳細設計の `05-security.md` を参照してセキュリティ対策を実装する
- **パフォーマンス**: 詳細設計の `07-performance.md` を参照してパフォーマンス対策を実装する
- **テスト駆動開発（TDD）**: 可能な範囲でTDDを採用し、特にService LayerやUtility Classesはテストを先に作成してから実装する
- **テストカバレッジ**: テスト計画書で定義されたカバレッジ目標を達成する
  - Server Actions: 80%以上
  - Service Layer: 90%以上
  - Utility Classes: 100%
  - Client Components: 70%以上
- **テストと実装の並行実施**: 実装と並行してテストを実施し、早期に問題を発見する

### 4.2 技術的な決定事項

- **データベース**: 開発環境はSQLite、本番環境はSupabase（PostgreSQL）
- **認証**: Clerkを使用（要件定義・基本設計で決定済み）
- **UIコンポーネント**: shadcn/uiを使用（技術スタックで決定済み）
- **フォーム処理**: Server Actions + Zodを使用（技術スタックで決定済み）

### 4.3 実装上の課題

- **SQLiteの型制約**: SQLiteではVarCharやText型のネイティブ型指定がサポートされていないため、スキーマから削除した（解決済み）
- **リレーション名の重複**: ProjectモデルでmembersとprojectMembersの両方がProjectMemberを参照していたため、projectMembersを削除した（解決済み）
- **編集権限の確認ロジックのバグ**: `existingTodo.projectId === existingTodo.projectId`という常にtrueになる条件があったため、修正した（解決済み）
- **カテゴリとタグのバリデーション不足**: 詳細設計で要求されているカテゴリとタグの存在確認・プロジェクト所属確認が未実装だったため、追加した（解決済み）
