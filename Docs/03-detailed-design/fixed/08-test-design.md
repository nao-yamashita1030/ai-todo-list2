# テスト設計

## 10.1 単体テスト設計

### テスト対象
- **Server Actions**: TODO作成、更新、削除、ステータス切り替えなど
- **Service Layer**: TodoService、ProjectService、CommentServiceなど
- **Utility Classes**: Validation、Authなど
- **Client Components**: TodoForm、TodoList、TodoItemなど

### テストカバレッジ目標
- **Server Actions**: 80%以上
- **Service Layer**: 90%以上
- **Utility Classes**: 100%
- **Client Components**: 70%以上

### テストケース例

#### TODO作成のテストケース
- 正常系: 有効なデータでTODOが作成される
- 異常系: バリデーションエラーが発生する
- 異常系: 権限エラーが発生する
- 異常系: データベースエラーが発生する

#### TODO更新のテストケース
- 正常系: 有効なデータでTODOが更新される
- 異常系: バリデーションエラーが発生する
- 異常系: 権限エラーが発生する
- 異常系: リソース不存在エラーが発生する

#### バリデーションのテストケース
- 正常系: 有効なデータがバリデーションを通過する
- 異常系: 必須項目が空の場合にエラーが発生する
- 異常系: 文字数制限を超えた場合にエラーが発生する
- 異常系: 不正な形式のデータでエラーが発生する

## 10.2 結合テスト設計

### テスト対象
- **APIエンドポイント**: POST、PATCH、DELETEエンドポイント
- **画面遷移**: 各画面間の遷移
- **データフロー**: データの作成から表示までのフロー

### テストシナリオ

#### シナリオ1: TODO作成から表示までのフロー
1. ユーザーがログイン
2. プロジェクト一覧を表示
3. プロジェクトを選択
4. TODO作成画面を表示
5. TODOを作成
6. TODO一覧に作成したTODOが表示される
7. TODO詳細画面でTODOの内容が正しく表示される

#### シナリオ2: TODO更新フロー
1. ユーザーがログイン
2. TODO一覧を表示
3. TODOを選択
4. TODO編集画面を表示
5. TODOを更新
6. TODO一覧に更新されたTODOが表示される
7. 変更履歴に更新履歴が記録される

#### シナリオ3: プロジェクト共有フロー
1. プロジェクトオーナーがログイン
2. プロジェクトにメンバーを追加
3. メンバーがログイン
4. メンバーがプロジェクトのTODOを閲覧できる
5. メンバーがTODOを作成できる
6. メンバーがTODOを編集できる

## 10.3 テストデータ設計

### テストデータ要件
- **ユーザーデータ**: 複数のユーザー（オーナー、メンバー、非メンバー）
- **プロジェクトデータ**: 複数のプロジェクト（公開、非公開）
- **TODOデータ**: 複数のTODO（異なるステータス、優先度、期限日）
- **コメントデータ**: 複数のコメント
- **変更履歴データ**: 複数の変更履歴

### テストデータ作成方法
- **開発環境**: シードスクリプトを使用
- **テスト環境**: テストデータベースを使用
- **E2Eテスト**: テスト実行前にテストデータを投入

### テストデータ管理
- **バージョン管理**: テストデータをGitで管理
- **リセット**: テスト実行前にテストデータをリセット
- **分離**: 各テストケースでテストデータを分離
